Your identity provider decides who works here. With directory sync, ac·modern:

- **Adds people** with their title and manager (turn off **Add new people automatically** to only update people who are already members)
- **Offboards or deactivates** people your IdP deactivates or removes
- **Reactivates** people the IdP re-enables, if it was the IdP that deactivated them. Someone offboarded by hand stays offboarded.
- Maps **IdP groups** to ac·modern admins, or to access levels

Set it up in **Settings → Directory sync**. One directory per organisation.

## SCIM

<Steps>
  <Step title="Choose SCIM and connect">
    Then **Generate token**. It's shown once; generating a new one stops the old one working.
  </Step>
  <Step title="Configure your IdP">
    <Tabs>
      <Tab title="Authentik">
        SCIM is in Authentik's free edition.

        1. **Applications → Providers → Create → SCIM Provider.** URL: `https://<your ac·modern>/scim/v2`. Token: the SCIM token. To send only some groups, set a **Group filter**.
        2. **Applications →** your ac·modern application **→ Edit → Backchannel providers:** add the SCIM provider. Authentik pushes all matching users and groups straight away, then each change as it happens. To resend everything, open the provider and click **Run sync again**.

        Deactivating someone in Authentik sends `active: false`, and deleting them removes them; ac·modern treats both as leaving. ac·modern takes the address from the user's email, not their Authentik username.

        Authentik has no title or manager fields. To send them, keep them in user attributes and add a SCIM property mapping (**Customization → Property Mappings → Create → SCIM Provider Mapping**) to the provider, alongside the default user mapping, for example:

        ```python
        return {
            "title": request.user.attributes.get("title", ""),
            "urn:ietf:params:scim:schemas:extension:enterprise:2.0:User": {
                "manager": {"value": request.user.attributes.get("manager_email", "")},
            },
        }
        ```

        The manager can be their email or their SCIM id in ac·modern.

        <Tip>If Authentik is also the source of truth for Google Workspace (Authentik Enterprise), sync ac·modern from Authentik, not Google, so both follow the same directory.</Tip>
      </Tab>
      <Tab title="Okta">
        Create an app integration with SCIM 2.0 provisioning, using header authentication (Bearer token). Base URL: `https://<your ac·modern>/scim/v2`, unique identifier `userName`. Enable *Create users*, *Update user attributes* and *Deactivate users*. Use **Push Groups** for the groups you want to map.
      </Tab>
      <Tab title="Microsoft Entra ID">
        **Enterprise applications → New application → Create your own (non-gallery) → Provisioning → Automatic.** Tenant URL: `https://<your ac·modern>/scim/v2`. Secret token: the SCIM token. Assign the users and groups to provision and start provisioning.
      </Tab>
      <Tab title="JumpCloud / OneLogin">
        Add a custom SCIM 2.0 application with the same base URL and a Bearer token, then enable user and group provisioning.
      </Tab>
    </Tabs>
  </Step>

The endpoints are documented in the [SCIM reference](/api-reference/scim). Managers come from the enterprise extension's `manager` attribute.

## Google Workspace

ac·modern reads your users and groups through a Google Cloud service account with read-only, domain-wide delegated access. Setup takes about 10 minutes, and **Settings → Directory sync** walks you through it, with the client ID and scopes ready to copy.

Suspended and archived users count as inactive. Managers come from the user's *manager* relation.

## Okta API

Create an API token (**Security → API → Tokens**) as a read-only administrator, and enter your Okta domain (`acme.okta.com`) and the token. Users in states other than active, password expired, locked out or recovery count as inactive. The built-in *Everyone* group is skipped. Managers match when the profile's `managerId` (or `manager`) holds an Okta user id or email.

## Microsoft Entra ID

Register an app with the **application** permissions `User.Read.All` and `GroupMember.Read.All` (grant admin consent), create a client secret, and enter the tenant ID, client ID and secret. Guests are skipped, disabled accounts count as inactive, and group membership includes nested groups.

## When someone is deactivated

| Setting | Effect |
|---|---|
| **Offboard (remove all their access)** | The same as [offboarding](/guides/offboarding): removals open for everything they hold, with the reason *Removed in the IdP*. |
| **Only deactivate them here** | Their ac·modern account is deactivated and their access is left alone. |

Owners are never deactivated by the directory. It logs that you need to do it by hand.

## Group mappings

Under **Groups**, map any IdP group to:

- **ac·modern admins:** members of the group become admins. Leaving the group makes them members again. Owners and admins you made by hand aren't touched.
- **An access level** (for example *github-owners* means *GitHub · Owner*): group members are treated as holding that access. It's detected and recorded as a grant with the source *IdP*, and ends when they leave the group.

<Warning>
  Access detected from an IdP group without a matching request is listed in the [audit evidence](/compliance/audit-evidence) as *Detected in the IdP without a request*. That makes the sync a detective control. Access requested and approved here first isn't flagged.
</Warning>

## Switching directories

Choosing a different source clears the old directory's records and its group mappings. People, their roles and their access stay; nobody is deactivated by the switch.
